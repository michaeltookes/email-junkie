### ~~12: Stale-thread / conflict detection before send~~
**Resolved**: 2026-07-28 (branch stale-thread-detection)
**Description**: An approved reply is no longer sent into a conversation that moved on since the draft was written — the stale-send that is silent and embarrassing in auto-send mode. Just before dispatch, `threadStalenessVerdict` re-fetches the source thread (a subject search in the draft's source mailbox plus a since-dated subject search in Sent) and a pure `StaleThreadCheck.verdict` classifies it as `.fresh` or `.stale(reason)` across three cases: **source missing** (the message was archived/deleted/moved — its UID is absent from a fully-seen thread), **newer reply in thread** (a message with a higher UID than the source arrived after it — UID monotonicity is used as the "arrived after" signal since envelope dates are raw strings), and **already replied** (a message from the user is in the thread in Sent since the draft was generated). Subject matching is normalized (leading `Re:`/`Fwd:` stripped, case-folded) so unrelated threads sharing a subject don't trigger, and "source missing" is only claimed when the search wasn't truncated. The check **fails open** — a transient search error, a provider that can't search, or an unknown source mailbox returns `.fresh` — so freshness detection never becomes a new way to block a valid send. Enforcement is wired into both live dispatch paths: the preview sheet's `approveDraftPreview` throws `DraftDispatchError.staleThread(reason)` and shows a confirmation dialog (send/save anyway or cancel); the review queue's `approveDraft` raises a per-draft `pendingStaleWarnings` entry and the card shows an inline conflict banner offering **discard / regenerate / send-anyway**. Both dispatch methods take a `force` flag for the "send anyway" override; `regeneratePendingDraft` re-drafts a fresh reply from the source message (`draftAndEnqueue` gained `requireWatching` so regeneration works outside the watcher loop). Especially important in auto-send mode, where the notification "Approve" routes through the same guarded `approveDraft`. 27 new tests: the pure evaluator across representative thread-change cases (fresh, source-missing, newer-reply, already-replied, precedence ordering, unrelated-subject, truncation), the IO verdict (fail-open, unknown-mailbox), and dispatch integration (preview + queue block, force override, regenerate).
**Review follow-up 2026-07-28**: Hardened the stale-thread guard after PR review. Sent-folder search failures no longer mask source-mailbox evidence of `sourceMissing` or `newerReplyInThread`; only the unavailable Sent result is treated as empty. Sent matches remain post-filtered against the exact draft generation timestamp after IMAP's day-granularity `SINCE`. Related-thread detection now follows envelope `Message-ID` / `In-Reply-To` links among subject matches, including parent links from the source envelope, so indirect multi-party replies and user replies to intermediate messages are recognized without relying on subject alone. Notification approvals that hit a stale warning now open Review Drafts so the inline action cannot appear to have completed silently while the draft remains pending. Added focused regressions for those paths.
**Review follow-up 2026-07-28**: A later review pass covered the remaining regeneration and blank-subject edge cases. Empty or prefix-only subjects now inspect bounded recent pages from the source mailbox and Sent instead of skipping freshness checks entirely. Regeneration preserves the original draft's staleness baseline, immediately re-checks the replacement so a manual reply still blocks duplicates, and collapses any already-queued replacement with the same draft identity before persisting. Added regressions for blank-subject newer replies/already-replied detection, manual-reply regeneration, and duplicate replacement identities.
**Review follow-up 2026-07-28**: Sent-date filtering now handles RFC 5322 date comments such as trailing timezone comments before comparing against the draft generation timestamp. If a related Sent message still has an unparseable date, the stale-thread guard treats it conservatively as post-generation so a possible manual reply is not dropped. Added regressions for commented post-generation dates, commented pre-generation dates, and unparseable related Sent dates.
**Review follow-up 2026-07-28**: Approval and regeneration now revalidate the current mail credentials after async stale-thread/source lookups before dispatching, saving, fetching a replacement body, or replacing a queued draft, so disconnecting or switching accounts mid-flight cannot use stale credentials or mix old envelopes with a new mailbox. Preview-sheet stale warnings now include a Regenerate action, backed by the same newest-related-message selection as queued drafts. Added regressions for queue approval, preview approval, queued regeneration after account changes, and preview regeneration.
**Review follow-up 2026-07-28**: Same-subject thread matching now requires Message-ID/In-Reply-To linkage when those identifiers are available; same-sender or same-recipient matching is only a fallback when provider envelope data lacks thread identifiers, preventing independent conversations with generic subjects from blocking fresh drafts. Blank-subject source scans now stop once they reach the source UID boundary and otherwise cap the broad mailbox fallback at bounded recent pages, leaving the result inconclusive instead of exhausting huge mailboxes. Added regressions for unlinked same-sender subjects and blank-subject scan bounds.

### ~~13: Low-confidence / "needs info" draft handling~~
**Resolved**: 2026-07-27 (branch low-confidence-drafts)
**Description**: The assistant no longer fabricates a confident reply when it lacks information only the user has. The draft prompt now instructs the model to emit a `NEEDS_INFO:` sentinel (a one-line reason plus bulleted missing items) instead of guessing when a reply would require a fact, date, decision, number, price, or attachment absent from the thread; `DraftGenerator` parses the raw output into a `DraftOutcome` — `.ready(body)` or `.needsInfo(DraftNeedsInfo)` — as distinct cases so a "needs input" result can never be mistaken for a sendable reply. The sentinel is only honored as the first non-empty line, so a normal reply that merely mentions the phrase isn't misclassified, and a sentinel with no summary still gets a readable fallback. A flagged `Draft` carries the `DraftNeedsInfo` (summary + missing items) and an empty body, persisted through the pending queue and surviving relaunch. The load-bearing guarantee — **no auto-send ever fires on a flagged draft** — is enforced at every dispatch entry point (preview send/save, `approveDraftPreview`, and the queue's `approveDraft`, which also covers the notification "Approve" action in auto-send mode), each refusing with a clear `needsUserInput` error and leaving the draft for the user to resolve. In the UI, a shared `DraftNeedsInfoView` shows the "Needs your input" summary and missing items in place of the reply body in both the preview sheet and the pending-approval card; the Send/Save/Approve button is hidden for a flagged draft (Deny becomes "Dismiss"), the queue card gets an orange badge and border, and the native notification uses a distinct "needs your input" title with a Deny-only category (no "Send Now"/"Save Draft"). 25 new tests across outcome parsing, the AppState no-dispatch guarantee from every path, and the notification action sets. The remaining sub-clause — flagged items appearing in an **activity history** — is deferred to item 21 (activity history is not yet built).

### ~~49: Bulk cleanup silently under-selects on large mailboxes~~
**Resolved**: 2026-07-26 (branch attnet-verify)
**Description**: Fixed the bug where a single bulk "clean all" over a filter left messages behind on a big mailbox (found live on att.net: a `from:bloomingdales` filter of ~923 cleared ~605 and stably left ~318). Added opt-in IMAP protocol logging (`IMAPDiagnosticLog`, gated by the `EMAILJUNKIE_IMAP_LOG` env var) and instrumented the selection walk; run live it showed `EXISTS=10000` with every window scanned and every window resolving exactly as many UIDs as its SEARCH returned — proving our scan was complete and pinning the true cause: **att.net/Yahoo exposes only ~10,000 messages over IMAP at once**, so a single pass can only reach matches inside that window and older mail is invisible until the visible ones are removed. The earlier "605 ≈ 8 KB frame" theory was a coincidence; the resolve step drops nothing. The fix is a **verify-until-stable sweep**: for move actions on the filter path, `applyBulkCleanupSweep` loops preview→apply until the filter reports zero or a pass makes no progress, draining a mailbox of any size (mark read stays single-pass since it removes nothing; the checkbox path stays a single pass on the picked UIDs). Live testing then surfaced Yahoo **rate-limiting** the rapid back-to-back scans ("SEARCH Server error - Please try again later"), which a single transient error aborted — so the sweep now **paces** (~1.2 s between passes, zero in tests) and **retries transient failures with backoff** up to a ceiling, failing fast only on genuine rejections; on giving up it preserves partial progress ("Moved N before the server asked us to slow down. Wait a moment and run it again"). A Stop button supersedes an in-flight sweep, the move confirmation warns it runs in repeated passes and may exceed the visible count, and sweep progress shows an ever-growing "N moved so far". Termination is guarded three ways (filter empty, zero-progress pass, 200-pass ceiling). The bulk apply half was split into `IMAPBulkCleanupHandler+Apply` and the sweep into `AppState+BulkCleanupSweep` to stay within length limits. **Live-verified end-to-end**: the `bloomingdales` filter drained from ~923 to a clean 0 on the real att.net Inbox. ~40 new tests across package and app (convergence 605→318→134, no-progress/empty stops, mark-read-does-not-sweep routing, transient-retry recovery and partial-progress-past-ceiling, transient-vs-permanent classification, consent copy).

### ~~45: Large-mailbox search exceeds IMAP frame limit (`PayloadTooLargeError`)~~
**Resolved**: 2026-07-22 (branch bulk-cleanup, merged to main)
**Description**: Fixed the crash that made the app unusable on the very mailboxes it exists to rescue. On a large mailbox the browser's default view issued `UID SEARCH`, whose `* SEARCH …` reply lists every matched UID on one line; above ~1,000 UIDs (~8 KB) swift-nio-imap's fixed frame decoder threw `PayloadTooLargeError` ("Couldn't reach the mail server."), found live on a real att.net inbox. Since `IMAPClientHandler` hardcodes `maximumBufferSize = IMAPDefaults.lineLengthLimit` (8192) and does not expose it, the fix avoids unbounded SEARCH entirely rather than raising the cap. **Unfiltered/default view:** a new bounded sequence-number path (`IMAPMessagePage` / `SequencePageRange`) `SELECT`s to read `EXISTS` for the total and `FETCH`es the newest page by sequence range, with a snapshot count so later pages stay stable as mail arrives/deletes — works at any mailbox size with no SEARCH. `MailProvider.fetchMessagePage` is a default-implemented protocol method so existing conformers keep working; the app routes the unfiltered browser through it and pages by offset. **Filtered/broad search:** a genuinely oversized `* SEARCH` reply is now caught and mapped to a clear, actionable `MailError.resultTooLarge` ("Too many messages matched to list at once. Narrow your search…") instead of a raw decoder error. The bounded-selection engine this established was the prerequisite for item 42's windowed bulk cleanup, which reuses the same `SequenceWindow` walk to avoid unbounded SEARCH when selecting large sets. Also fixed a UX confusion surfaced in the same work: the browser's folder picker now reloads immediately on change instead of leaving stale results until the next manual search. Tests cover `SequencePageRange` math, the bounded fetch state machine, and the overflow→`resultTooLarge` mapping (including an `errorCaught` wiring test that replaced an earlier end-to-end test which hung the suite). Live-verification against the real att.net Inbox is item 44.

### ~~42: High-volume inbox cleanup & bulk triage~~
**Resolved**: 2026-07-23 (branch inbox-cleanup)
**Description**: Delivered the bulk-cleanup engine for mailboxes drowning in unread junk, provider-agnostic across every account reachable over the IMAP path (Gmail, Yahoo/AT&T, other IMAP) via the item-41 `MailboxNaming` layer. The core problem was that a bulk filter can match tens of thousands of messages, but a single `UID SEARCH` returns every matching UID on one response line and overflows NIO-IMAP's 8 KB frame cap — the same failure that broke plain search on large mailboxes (item 45). So selection walks the mailbox in **bounded sequence windows** (`SequenceWindow.windows` tiles `1...total` newest-first with no gap or overlap, 500 per window), making the server's reply bounded by construction at any mailbox size; `SequenceWindow.batches` bounds the outbound UID set for `STORE`/`MOVE` the same way. `IMAPBulkCleanupHandler` drives `LOGIN → SELECT → SEARCH sequence windows → FETCH UIDs → [sample FETCH | UID STORE/MOVE in batches] → LOGOUT`, exposed as `previewBulkCleanup` / `applyBulkCleanup` on `MailProvider` (default-unsupported, so existing conformers are unaffected). Two ordering properties make it safe on a live mailbox: **selection completes fully before the first mutation** (a `UID MOVE` renumbers the sequence space a scan is still walking, so interleaving them would silently misnumber every later window — pinned by a test), and preview **only ever reads** (asserted: no `STORE`/`MOVE` on the preview path). Actions are limited to `markRead` / `archive` / `moveToTrash` — every one either in-place or a move to a recoverable folder, with permanent `UID EXPUNGE` deliberately out of scope and a test asserting no destructive action lacks a destination. In the app, `BulkCleanupPanel` sits under the browser's filters as a two-step flow: **Preview** reports the match count plus a sample, and only then does a run button appear; destructive actions additionally require confirming an alert naming the exact count and the recovery path. The safety anchors are the previewed account, query, UIDVALIDITY, and concrete UID set — apply refuses stale app context and sends exactly the previewed UIDs, so editing filters, switching accounts/folders, or receiving later matching mail does not silently clean an unseen set. A selection cap (5,000/pass) keeps one run bounded and reports `isPartial`, so a capped scan is worded "at least N" rather than presented as exact; `markRead` narrows eligible candidates to unread messages so repeated capped passes advance instead of reprocessing already-read UIDs; progress is reported per completed batch, and a rejected `UID MOVE` explains the server may lack MOVE support instead of surfacing a bare `BAD`. Hardening from review: the apply path bounds its batch index rather than trusting server tag ordering (an unsolicited/duplicated tagged response would otherwise crash mid-cleanup), keys the batch command off the action rather than the presence of a destination so a misconfigured move fails loudly instead of silently marking mail read, binds preview approval to the account that produced it, ignores stale preview/apply callbacks after account switches, applies only the previewed UID set after revalidating UIDVALIDITY and current UID presence, and aborts sequence-window selection if an EXPUNGE/VANISHED response could renumber pending sequence results. 72 new tests (49 package: window tiling/coverage/bounds, batching, action semantics, mark-read candidate narrowing, progress math, plus the full `EmbeddedChannel` state machine covering windowed selection, preview sampling, cap/partial, exact-cap wording, previewed UID application, mailbox mutation aborts, pre-apply UID revalidation, mark-read, both moves, selection-before-mutation, progress, and auth/move-rejection/overflow/dropped-connection failures; 23 app: preview/apply flow, account/action/filter/folder-change invalidation, stale callback handling, error surfacing, and confirmation copy). The **monitoring view** (breakdowns by sender/domain and by age) was deliberately deferred and is now **item 46**. Not yet live-verified against the real `att.net` account — in particular the live `Trash`/`Archive` folder names (item 44).

### ~~5: Inbox watcher~~
**Resolved**: 2026-07-13 (branch inbox-watcher)
**Description**: Added a timer-driven inbox watcher that polls while the Mac is awake and turns new, replyable messages into queued drafts. `InboxWatcher` (the scheduling half) owns a repeating `Timer` and `NSWorkspace` sleep/wake handling — it pauses the timer on sleep and resumes with an immediate catch-up poll on wake, single-flighting ticks so polls can't stack. The poll *policy* lives on `AppState` (`pollInboxOnce`): fetch the recent inbox (envelope-level), and for each message that is new and replyable — oldest first, so drafts read chronologically — generate a reply via the existing draft engine and enqueue it to `pendingDrafts` (driving `pendingDraftCount`). A message is marked processed the moment it is selected for drafting, so it is never drafted twice even across restarts (transient-failure retry is deferred to item 27). Processed identity uses the RFC 5322 Message-ID when present, falling back to `UIDVALIDITY:UID`; the bounded (1000-key, oldest-evicted) `ProcessedMessages` set persists to `ProcessedMessages.json`. Watching auto-starts at launch when an account + LLM are connected, is pausable from a new menu-bar "Start/Pause Watching" control, reschedules on a poll-interval change, and stops on disconnect. Reply-worthiness is a light gate for now (real sender, not self) — fuller filtering is item 17. 19 new tests (9 `ProcessedMessages`, 10 watcher: dedup across polls, chronological enqueue, skip-self/processed, fetch-error, mark-processed-on-failure, lifecycle transitions). Refactored the message-preview actions into `AppState+MessagePreview.swift` to keep `AppState.swift` within the file-length limit.
